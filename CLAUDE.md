# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Bucketeer is a self-service S3 portal for Ceph clusters managed by **croit**. Users log in with AD, get their S3 (RGW) access/secret keys with ready-to-paste `~/.aws/config` and `~/.aws/credentials` snippets, and manage their buckets: create, delete, versioning, sharing, scoped keys, lifecycle, and the full set of S3 bucket features. Every bucket has a quota in TiB that is billed (chargeback sheet). Optionally (Phase 6) people also get AWS buckets and keys in one shared AWS account ("Cloud"), and the database is backed up nightly. Admins get an admin page. See "Product design" below for decisions already made, and `TODO.md` for the phased plan.

See `TODO.md` for what exists so far; `PLAN.md` is the Phase 6 design record (this file is authoritative where they differ). Code layout: `app.py` (uvicorn entry point), the `bucketeer/` package (`config.py` settings, `main.py` app factory, `croit.py` croit client, `rgw_admin.py` RGW Admin Ops client (the `rgw` admin backend), `db.py` SQLite storage, `s3docs.py` shared bucket policy/lifecycle/tag helpers, `ldapauth.py` AD login, `auth.py` sessions/CSRF/throttle/login routes, `rgw_user.py` RGW user resolution, `credentials.py` keys/snippet API, `admin.py` admin API, `admin_settings.py` + `policy_settings.py` admin settings, `profile.py` + `budget.py` user profile, `s3client.py` user S3 clients, `buckets.py` bucket API, `bucket_ops.py` backend-specific bucket create/versioning, `bucket_quota.py` + `catalog.py` bucket quotas and product catalog, `bucket_facts.py` managed fact tags, `rebuild.py` rebuild SQLite rows from Ceph, `bucket_keys.py` bucket keys, `subusers.py` subusers, `lifecycle.py` simple lifecycle rules, `lifecycle_rules.py` full editor, `policy_editor.py` raw policy editor, `cors.py` CORS rules editor, `notifications.py` bucket notifications, `share_links.py` presigned share links, `sharing.py` sharing with AD users, `audit_viewer.py` admin audit log viewer, `offboarding.py` daily offboarding job, `backup.py` nightly backup and restore, `billing.py` usage samples and charges, `billing_report.py` chargeback .xlsx and monthly email, `acl.py` bucket/object ACLs, `cloud.py` AWS admin client, `cloud_users.py` cloud IAM users and keys, `cloud_buckets.py` cloud buckets, `cloud_sharing.py` sharing cloud buckets with people, `cloud_delete.py` cloud bucket delete jobs, `admin_cloud.py` cloud buckets in the admin views, `cloud_costs.py` cloud costs from the AWS data export, `location.py` storage location), `static/` (frontend, served at `/`), `tests/`, and `mock/` (dev/test-only mock croit API and RGW Admin Ops API). - **Backend:** Python + FastAPI. It is the only component that talks to the croit API. The browser never calls croit directly and never sees a croit token.

## Configuration

- All runtime config comes from environment variables loaded from `.env`. Use `python-dotenv` without override, so variables already in the process environment (such as the ones systemd sets) take precedence.
- `.env` is git-ignored and holds real values and secrets. `.env.default` is committed and documents every variable. Each one is marked either:
  - **REQUIRED**: left empty in the file, and the app refuses to start until it is set. Never fall back to a placeholder.
  - **Default**: the value in the file must match the default in the code, so a missing line behaves the same as the template.
- Whenever you add a variable to the code, add it to `.env.default` with the same kind of comment.
- `PORT` is required and is the port the server listens on. `.env.default` must define it.
- Put comments on their own lines. systemd's `EnvironmentFile` treats a trailing `# ...` as part of the value.

## Authentication

Users log in with Active Directory credentials over LDAPS, using the `LDAP_*` settings. The portal does its own AD login and does not use croit's `/auth/login`. The flow:
1. Bind as the service account (`LDAP_BIND_DN`).
2. Search `LDAP_USER_FILTER`, with `{login}` replaced by the LDAP-escaped text from the login form. The filter matches `sAMAccountName`, `mail` or `userPrincipalName`, so **both username and email address work**.
3. Require **exactly one** match. `mail` is not unique in AD, so refuse an ambiguous login rather than picking one.
4. Check membership of `LDAP_REQUIRED_GROUP_DN`. Use the `LDAP_MATCHING_RULE_IN_CHAIN` OID (1.2.840.113556.1.4.1941) so nested groups count.
5. Bind as the found DN with the user's password to verify it. Reject empty passwords: AD treats an empty password as an unauthenticated bind, and that bind succeeds.
6. Take the user's identity (and RGW uid) from `LDAP_USERNAME_ATTRIBUTE` (`sAMAccountName`), never from the typed login. That way username and email logins reach the same S3 user.

**Code:** `bucketeer/ldapauth.py` (`AdAuthenticator`, ldap3 run via `asyncio.to_thread`) and `bucketeer/auth.py`.
- **CA file fetch** (`bucketeer/ldapca.py`, tests `tests/test_ldapca.py` with a fake TLS server): `LDAP_CA_CERT_FILE` defaults to `data/ldap-ca.pem` (empty = system trust store; ignored with `LDAP_TLS_VERIFY=false`). `load_settings` fetches the CA certificates the first reachable LDAP server presents (TLS handshake only, no password, no LDAP request; never the server's own certificate; kept only if the server certificate then verifies against them) when the file is missing, or when the hosts in `LDAP_URL` differ from the record `<file>.hosts` (a hash written at each fetch; a file supplied by hand is adopted, not replaced, until the hosts change). It logs old and new SHA-256 fingerprints; a failed fetch keeps the old file. Same by hand: `python3 app.py --fetch-ldap-ca [--force]`. It is trust on first use, so `LDAP_CA_SHA256` pins it (comma-separated list; only matching CAs are kept). The fetch asks EVERY server in `LDAP_URL`, keeps the union of pinned CAs, skips (and logs) a server that is down, sends no pinned CA or fails the check, and needs one to pass. **Pinned root (owner, 2026-11-21: "fixes itself"):** when a server sends no pinned CA and a pin is set, `directory_lookup` binds with the service account over TLS checked against the CAs that server sent (TOFU for that login, logged) and reads every `cACertificate` under `CN=Public Key Services,CN=Services,<configurationNamingContext>`; only a pinned one is kept, and the file holds only pinned CAs, so the final verify proves the chain reaches it. Domain controllers usually send only an intermediate CA: `ldapauth` wraps ldap3's `create_default_context` to add `VERIFY_X509_PARTIAL_CHAIN` (Python 3.13+ default), so an intermediate in the file is a trust anchor, and the fetch's own verify check uses the same flag. At startup `ldapca.startup_report` (called from the lifespan) logs the user, working folder, settings file, CA file with fingerprints and pin state, and warns when `.env` is readable by group/others or the file lacks the pinned CA. `app.py` sets up logging before `load_settings`, so the fetch messages reach the log.
- LDAPS only: `Settings` refuses `ldap://` URLs (and a filter without `{login}`). URLs are tried in order for the service bind; user bind and group checks stay on that server. `{login}` is always RFC 4515-escaped. Group checks are a base-scope search on the user's DN with `memberOf:1.2.840.113556.1.4.1941:=<group>`.
- Failures: `InvalidCredentials` (wrong password, unknown user, ambiguous match, not in group, empty input; one uniform message to the user, the specific `.reason` only in the INFO log and audit `details`) versus `LdapUnavailable` (503). Empty passwords, and ones ldap3's SASLprep would reject (control characters), are refused as bad passwords before any connection; otherwise they would show up as 503 and tell an attacker which accounts exist. A rejected service bind fails the login at once (503) without trying other servers, so a stale service password cannot lock the service account; only connection errors fail over. Never log or audit a password.
- Tests inject a fake connector (`AdAuthenticator(settings, connector)`; `create_app(..., authenticator=, clock=)`), see `tests/test_auth.py`. No network.
- **Session:** stateless signed cookie (itsdangerous, `SESSION_SECRET`), name `__Host-bucketeer` (`bucketeer` when `SESSION_COOKIE_SECURE=false`), `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, `Max-Age=SESSION_MAX_AGE`. Payload is only `username` (the sAMAccountName; the RGW uid is resolved from it, see "RGW user resolution"), `display_name`, `email`, `is_admin`, `issued_at`; never a password or S3 key. Expiry is also enforced server-side from `issued_at`. Every login issues a new token. Because it is stateless, logout cannot revoke a copied cookie before it expires.
- **Routes:** `POST /api/login` (JSON `{login, password}`), `POST /api/logout`, `GET /api/me`. Statuses: 401 uniform failure, 429 throttled (`Retry-After`), 503 LDAP down, 400 malformed body. Login/logout write audit actions `login.success`, `login.failure`, `login.throttled`, `logout`.
- **Dependencies for later endpoints:** `Depends(auth.require_user)` returns the `SessionUser` (401 if none), `Depends(auth.require_admin)` adds a 403 for non-admins. Take the identity from the session, never from the request. Endpoints that act on the user's RGW account use `Depends(rgw_user.require_rgw_user)` instead (see below).
- **CSRF rule:** every state-changing (non GET/HEAD/OPTIONS) `/api` request must send `X-Requested-With: bucketeer`, else 403. `create_app` enforces it by including all `/api` routers into one `APIRouter(prefix="/api", dependencies=[Depends(csrf_protect)])`: add new routers there (`api.include_router(...)`), never register `/api` routes straight on `app`. The frontend's fetch helper must always send the header. Never add CORS middleware that allows that header, and never make a GET change state.
- **Throttle:** in-memory `LoginThrottle`, constants in `auth.py`: 10 attempts per normalized typed login, 10 password checks per resolved account (`resolve()` then `verify()`, so sAMAccountName/mail/UPN count together and stay below AD's lockout threshold) and 20 per client IP in 15 minutes, then 429 without contacting LDAP. The message stays "Too many attempts" (Q3). The limit of 10 is the owner's choice, so make sure it stays below the AD lockout threshold. Attempts count when they start and are refunded on success or LDAP outage. It resets on restart (single process assumed). The IP is `request.client.host`, which is correct only because uvicorn runs with `proxy_headers` and `forwarded_allow_ips="127.0.0.1"`.

The backend calls croit as a single service identity, with `CROIT_API_TOKEN` sent as a Bearer token. Because of that, the backend must make sure a user only ever reads or changes their own RGW uid.

## Deployment: appmotel

The app has to deploy unmodified on [appmotel](https://github.com/dirkpetersen/appmotel) (`appmo add bucketeer <user/repo>`). appmotel is a small PaaS: systemd user services behind a Traefik HTTPS reverse proxy. Its detection rules shape the repo layout:

- **Entry point:** `app.py` at the repo root. appmotel starts it as `.venv/bin/python3 app.py` with the repo root as the working directory, so `app.py` must call `uvicorn.run(...)` itself, reading `PORT` from the environment. There is no `start.sh` or Procfile.
- **Dependencies:** `requirements.txt` at the repo root. appmotel creates `.venv` and runs `pip install -r requirements.txt`. It does **not** install from `pyproject.toml`.
- **`install.sh`** (optional) runs on every deploy and update, from the repo root.
- **`.env` handling:** on first deploy, appmotel copies `.env.default` to its config directory as `.env` and symlinks `repo/.env` to that copy. It also passes the file to systemd as `EnvironmentFile`. It replaces any `PORT` below 10001 with a port it assigns itself (10001–59999), so a low default such as `PORT=8000` works for local development. Operators edit the live file with `appmo env bucketeer`.
- **Value restrictions:** appmotel's `.env` parser skips any value containing `$(`, a backtick, `;`, `&&`, `||`, or an unquoted `|`. Secrets with those characters, such as a croit service-account password, must be quoted, or avoid those characters.
- **Proxy:** Traefik terminates TLS and forwards to `http://localhost:$PORT`. Bind to `127.0.0.1`, and run uvicorn with `proxy_headers=True` and `forwarded_allow_ips="127.0.0.1"` so request scheme and URLs come out as `https`. Mark session cookies `Secure`.
- **Health check:** set `HEALTH_CHECK_PATH=/health` in `.env.default` and serve a cheap `GET /health` that doesn't call croit. Traefik polls it every 30s.
- **Layout gotcha:** a top-level or `src/` directory named `frontend`, `backend`, `api`, `worker`, `db` or `cache` that contains a `requirements.txt`, `package.json`, `pyproject.toml` or `go.mod` switches appmotel into multi-component mode. Keep everything in a single component: one `requirements.txt` at the root, and static assets in a directory such as `static/`.
- appmotel's `.env` also accepts `MEMORY_LIMIT`, `CPU_QUOTA`, `RATE_LIMIT_AVG`, `RATE_LIMIT_BURST` and `DISABLE_RATE_LIMIT`.

## croit API

- Spec: `docs/api/api-1.yaml` (OpenAPI 3.1, ~40k lines). Online docs: https://www.croit.io/api-docs. The file is too big to read whole, so grep for `^  /<path>:` and for `^    <SchemaName>:`.
- The spec has no `servers` entry, so the croit base URL has to come from an environment variable (see Configuration).

Endpoints this app relies on:

| Purpose | Call | Notes |
|---|---|---|
| Log in | `POST /auth/login` | HTTP Basic auth header + form body `grant_type=client_credentials`. Returns `Token` (`access_token`, `expires_in`, `roles`, `passwordNeedsChange`). Works for croit users and LDAP users when LDAP is configured. `POST /auth/login-form` is the variant that takes `grant_type=password` |
| Authenticated calls | `Authorization: Bearer <access_token>` | API tokens are sent this way directly and skip `/auth/login` |
| Session check/refresh | `GET /auth/token-info` | Calling it also extends the session |
| OIDC login (optional) | `/auth/oidc/*` | |
| Read S3 keys | `GET /s3/users/{uid}/keys` | Returns `RgwUserKey[]`: `{user, access_key, secret_key}`, and the keys can be null |
| Endpoint discovery | `GET /s3/users/{uid}/cfg-file/download` | Returns a `.s3cfg` whose text includes a running RGW gateway address and the DNS name. Useful for filling in `endpoint_url` |
| Create S3 user | `POST /s3/users` | `NewUserRequest`: `uid` and `name` are required. RGW rejects duplicate emails |
| Change keys | `PUT /s3/users/{uid}/keys` | **Replaces the whole key set** for the user and subusers, so any key left out is deleted. Always read-modify-write. Returns an async task |
| Add / remove one key | `PUT` / `DELETE /s3/users/{uid}/keys/{accessKey}` | Use these for creating and rotating keys |
| Suspend user | `PATCH /s3/users/{uid}` | `RgwUserUpdateRequest.suspended`, used by offboarding |
| Quotas | `PUT /s3/users/{uid}/quota`, `PUT /s3/buckets/{bucketName}/quota` | |
| Buckets | `PUT` / `PATCH` / `DELETE /s3/buckets/{bucketName}` | Create and delete return tasks. Deleting a non-empty bucket needs `deleteData` plus the confirmation sentence and the `ignoreWarning` token croit names in its first refusal (400 `IgnoreWarningResponse`) |

- RGW uids can carry a tenant (`tenant$uid`). URL-encode the `$` in path parameters.
- Errors come back as the `ErrorMessage` schema.
- `docs/api/s3-features.md` lists every S3 endpoint croit offers, and the S3 features users have to manage through the S3 protocol instead. `docs/api/README.md` covers how to get croit tokens.
- **Client:** `bucketeer/croit.py` (`CroitClient`, async httpx). `create_app` builds one per app (`app.state.croit`, `get_croit` dependency) and closes it on shutdown; tests pass `transport=httpx.ASGITransport(app=mock)` (see `tests/test_croit_client.py`). Methods return croit's JSON as plain dicts; task-returning calls (`create_bucket`, `delete_bucket`) return the task for `wait_for_task`.
  - Errors: `CroitError(status, code, message, details)` for non-2xx; `CroitWarning` (a `CroitError`) for a 400 `ignorableWarning`, with `.token` kept out of str/repr; `CroitUnavailable` for network/timeout; `CroitTaskFailed`/`CroitTaskTimeout` from `wait_for_task`.

Formats in the two files differ, so keep them straight:

- `~/.aws/config`: `[profile <profile>]` (bare `[default]` when the profile is `default`) with `region`, `endpoint_url` (the RGW gateway), `request_checksum_calculation` / `response_checksum_validation = when_required` (newer AWS SDKs/CLI send CRC checksums that many Ceph RGW versions reject) and `s3 =` / `addressing_style = <path|virtual|auto>` as the last, indented block. **Credentials API** (`bucketeer/credentials.py`, `/api/credentials`, uid only from the session via `require_active_rgw_user`, so suspended users get nothing): `GET` returns `{profile, region, endpointUrl, addressingStyle, keys:[{accessKey}]}` and **never a secret**; `POST /reveal {accessKey}` returns `{accessKey, secretKey}` only for a key found in the user's own croit key list (exact match, else 404), audits `credentials.reveal` (actor, uid, access key; **never the secret**) before answering, and sends `Cache-Control: no-store`. **Reveal rule (owner, 2026-10-27: two paths):** a secret key may leave the server only through that endpoint or through the one-time setup script (see "Setup command" below); no other response, log line, audit entry or error may contain one. The one exception is a cloud (AWS) key, whose secret exists only in the answer that creates it (see "Cloud users and keys"). The snippets are built in the browser (`static/js/awsconfig.js`) from the GET data plus the revealed secret; `secret-field` takes a `fetcher` so the secret exists in memory only while revealed (60 s) and is dropped on re-mask, key change or navigation. Never put a secret in a DOM attribute, URL, storage or console.
- **Setup command ("Set up this computer", owner decisions 2026-10-27):** normal users (Advanced OFF) get no key list, secret or snippets, only this panel; it shows in both modes. `POST /api/credentials/setup-link {os: windows|macos|linux}` (same router: CSRF, `require_active_rgw_user`) follows the effective storage location; for an on-prem link it picks the user's first own key (none: 409; no endpoint: 409) (cloud-only links: see "Cloud users and keys", Setup), stores `secrets.token_urlsafe(32)` as its SHA-256 only (table `setup_tokens`, migration v11, rows older than 1 day deleted on create) and answers `{url, command, expiresAt, expiresIn, os, location}`, `no-store`. Lifetime 15 minutes, at most 10 links per user per 15 minutes (429, counted in SQLite). Commands: `curl -fsSL -X POST '<url>' | sh` (macOS, Linux), `[Net.ServicePointManager]::SecurityProtocol = ... -bor 3072; irm -Method Post '<url>' | iex` (Windows, forces TLS 1.2 on PowerShell 5.1). `POST /setup/{token}` is outside `/api` (registered on the app before the static mount, no session, no CSRF header: the token is the only credential, `credentials.setup_router`). EVERY refusal is HTTP 200 with an error script (`curl -f` drops 4xx bodies, `irm` throws on them; the real reason is only in the audit): unknown token (`echo '...'`), used or expired (for that row's OS; atomic `UPDATE ... WHERE used_at IS NULL AND expires_at > now`, done BEFORE the secret is read); then the account must exist and not be suspended, the stored access key must still be an own key (admin trouble reading either: `admin_unavailable`), the endpoint known; access key and secret must match `^[A-Za-z0-9/+=]{1,128}$` (else refused, so nothing breaks out of the quoted strings). The browser keeps the link in memory only (`components/setup-panel.js`: OS tabs, command with Copy, countdown, "Download setup file instead": `.cmd`, `.sh`, or a zip made by `js/zip.js` so the macOS `.command` keeps its execute bit; the files hold only the token URL). Tests `tests/test_setup_link.py`, `tests/test_setup_script.py` (runs the sh script for real), `tests/test_zip_js.py` (needs node).

## `tools/`: standalone croit scripts

`tools/` holds admin scripts that use the croit API but are **not part of Bucketeer**. Keep them independent:
- Single-file, executable, standard library only.
- Configured through the shared `CROIT_*` environment variables (see `tools/README.md`), not Bucketeer's `.env`.
- Never import anything from the app, and never import tools code into the app.

`tools/croit-cert` installs the RGW/HAProxy TLS certificate through `PUT /config/rgw-ssl-cert`. When changing it:
- Keep it idempotent and keep its exit codes stable (0 ok/unchanged, 1 error, 3 `--verify` mismatch), since it is meant to run from cron or a certbot hook.
- Never call `/auth/logout`. croit allows one session per user, so logging out also ends that user's browser sessions.

`tools/croit-gate` is an allowlisting gateway, **optional and relevant only for `ADMIN_BACKEND=croit`** (the default `rgw` backend never talks to croit), that holds the real croit token (Bucketeer's `CROIT_URL` points at it, its `CROIT_API_TOKEN` is the gateway's client token). It installs itself outside the repo for its own Unix user (`croit-gate install`: `~/.local/bin`, a systemd user unit, `~/.config/croit-gate/env` 0600, never overwritten), so Bucketeer deploys don't touch it. **A new croit call in `bucketeer/croit.py` must also be added to the gateway's `ROUTES` table**; `tests/test_croit_gate.py` (AST drift test) fails until it is. Never log tokens or query strings in it (`put_key` carries a secret key in the query).

## Product design (decided by the owner)

### Two API planes

- **croit API** (admin plane, with `CROIT_API_TOKEN`): S3 users, keys, quotas, suspension, usage, and bucket create/delete, as listed in `docs/api/s3-features.md`.
- **Switching the admin plane to the RGW Admin Ops API (owner decision, 2026-10-14; croit support recommended it and supports it on Reef, and croit never overwrites S3 entities it didn't create).** Goal: Bucketeer needs no croit token at all, and its admin credential reaches only RGW. Plan (TODO.md "Phase 5"):
  - `bucketeer/rgw_admin.py` `RgwAdminClient` offers the same public methods and exceptions as `CroitClient`, so callers don't change. It signs requests with SigV4 through botocore, using an RGW service user that has only `users=read,write; buckets=read,write; usage=read; metadata=read` caps (metadata recommended; without it the user list falls back to `?list`) (`RGW_ADMIN_URL`, `RGW_ADMIN_ACCESS_KEY`, `RGW_ADMIN_SECRET_KEY`; use an internal RGW address, not the public S3 endpoint). Every path parameter is encoded; secrets never appear in logs, errors or audit entries.
  - `ADMIN_BACKEND=croit|rgw` chooses the backend during the transition. The default became `rgw` with A7; the croit backend is removed only after the cluster check. No fallback between backends at runtime.
  - Bucket create (with placement as `LocationConstraint`) and the versioning toggle move to the S3 data plane with the user's OWN key. Deleting a non-empty bucket becomes a Bucketeer background job with progress, since Admin Ops has no async task. Placements become an admin-entered allowlist, since Admin Ops can't list them. The endpoint comes from `S3_ENDPOINT_URL`, which is required with the rgw backend because there is no croit `.s3cfg`.
  - Tests run the same behaviour against both backends; the dev/test mock gets `/admin` routes that share state with the mock croit and moto.
  - The Admin Ops credential can still read every user's secret key, so it reaches all S3 data, just not the cluster. RGW accounts (Tentacle) are the next step down. `tools/croit-gate` is optional since A7 (only for `ADMIN_BACKEND=croit`) and goes away with the croit backend.
- **S3 API** (data plane, boto3 against `S3_ENDPOINT_URL`): everything croit lacks. That covers lifecycle, CORS, object-lock retention and legal hold, tagging, notifications, presigned URLs, bucket policies and ACLs.
  - S3 calls run with **the logged-in user's own keys**, fetched from croit on the server, so RGW itself enforces ownership, policies and object lock.
  - Never use an admin S3 identity for user actions. Keys stay on the server and never reach the browser except on the credentials screen.
- **AWS** (Phase 6, optional, `bucketeer/cloud.py`): Bucketeer's own IAM admin user manages people's IAM users, cloud buckets and the backup user; it never touches objects (an explicit Deny). People reach their cloud buckets with their own IAM keys only. See "Cloud (AWS)".

### Users and access

- Login requires membership of the AD group `LDAP_REQUIRED_GROUP_DN`. Opening it to all users later just means clearing that setting.
- The RGW uid is the **lowercased** AD `sAMAccountName` (Q4). At login, an existing RGW user whose uid matches case-insensitively (checked against croit's uid list) is used instead, with an audit entry. Admin uid mappings always win.
- Logging in with an email address or UPN only finds the account: the AD search resolves it to the `sAMAccountName`. A uid is **never** derived from an email address.
- The first login creates the RGW user automatically with an **unlimited** user quota (P6-4; was 1 TiB, Q4): growth is limited by bucket quotas and the weekly limit (see "Bucket quotas").
- **Never send an email address to croit when creating an RGW user (Q5).** `NewUserRequest` only requires `uid` and `name`, and email is optional, so the uid comes from the sAMAccountName (an email login is first resolved to the sAMAccountName through AD) and `email` stays empty. That also rules out RGW's duplicate-email rejection. Pass an email only if a future croit version makes it required, and then pass both.
- Admins are members of `LDAP_ADMIN_GROUP_DN`, plus the AD usernames listed in `ADMIN_USERS` (comma-separated, any case; checked after a normal AD login, owner 2026-11-21). They see all users and buckets, set quotas, suspend users, and edit settings.
- **Offboarding:** a daily job suspends (`PATCH /s3/users/{uid}` with `suspended`) every RGW user whose AD account is disabled or no longer in the group, together with that user's bucket keys. It never deletes anything; an admin decides what happens to the data.
- **Offboarding safeguards (Q10, owner accepted all four recommendations):**
  1. **Scope:** only RGW accounts Bucketeer knows belong to a person: accounts it created (first login or as a share/ACL recipient) or linked at login (resolved for a session user, case match included), and admin uid-mapping targets. Record each AD name <-> uid link durably when the resolver links it (a new migration; the audit log is not the source). Any other RGW user (service accounts, legacy users, bucket-key users as owners) is never touched by the job; bucket keys are suspended only through their owner.
  2. **Coming back:** a job suspension is recorded as made by `offboarding` (the user and their bucket keys, `suspended_by = 'offboarding'`). The person's next successful login unsuspends exactly those (the user and only keys with `suspended_by = 'offboarding'`), audited. Suspensions an admin made by hand are never undone automatically, and the job never touches an account an admin already suspended.
  3. **When AD looks wrong:** abort the whole run, suspending nobody, if AD can't be read (any lookup error, not just a full outage) or if more than 10% of known users or more than 20 people would be suspended in one run. The reason is shown on the admin page and audited.
  4. **Trial run first:** the job starts in report-only mode and shows on the admin page who would be suspended and why. An admin switches it to "enforce" in Settings (audited). It runs daily at 03:00 server local time by default, and an admin can also start a run by hand. Single process, in-process scheduler, never blocks startup or `/health`; one run at a time.
  - **Thresholds are admin settings (Q14, owner accepted the recommendation):** the abort rule becomes "more than `maxPercent` % of known people AND at least `minPeopleForPercent` people, OR more than `maxPeople` people", editable on the Offboarding tab with defaults 10 %, 4 and 20. So one or two genuine leavers go through on a small installation, while a mass misreading of AD is still stopped. Changes are audited (`admin.settings.offboarding`).

### RGW user resolution

`bucketeer/rgw_user.py`, `app.state.rgw` (`RgwResolver`). **The RGW uid comes only from the server session, through `Depends(require_rgw_user)` (or `require_active_rgw_user`, which also refuses suspended users with 403); never read a uid from the path, query, body or headers for the user's own account.** `require_rgw_user` returns an `RgwAccount` (`username`, `uid`, `status`, `display_name`, `quota`, `reason`) and answers 503 (unavailable) or 409 (creation failed); a `suspended` account is returned, so check `status` or use the active variant. `GET /api/account` (never raises, no keys) returns `{uid, status, reason, message, displayName, quota, created}` for the dashboard.
- **Order:** admin uid mapping (case-insensitive AD name, uid used verbatim; the target must already exist, else `mapping_target_missing`, uncached, nothing created) -> lowercased sAMAccountName, `tenant$` prefixed when `S3_TENANT` is set, validated (`[a-z0-9][a-z0-9._@+-]{0,63}`, else `creation_failed`/`invalid_username`); an existing uid matching in the same tenant (exact) with the bare uid case-insensitive (croit `/s3/user-names`) is used with audit `rgw.user.case_match` (two such uids: `ambiguous_uid`, refused) -> refused as `uid_taken` (audit `rgw.user.uid_taken`) if that uid is any mapping target or any `bucket_keys.rgw_uid` (revoked too; `uid_claimed`), so an unmapped AD user never shares someone else's account -> auto-create (`CroitClient.create_user` with uid and AD display name only; never an email, Q5) then the user quota set to unlimited (`policy_settings.UNLIMITED_USER_QUOTA`); audit `rgw.user.create` / `rgw.user.create_failed`. If the quota call fails after the create, the audit entry says `quota_applied: false`; the next resolve of that uid sees it as newest and retries (durable, no extra table; a later success entry `rgw.user.default_quota` settles it).
- **Admin Ops service user (rgw backend):** never resolved, adopted, mapped to or created for a person; see "Admin backends" (the check runs first in `_resolve`, on the mapping target or the lowercased sAMAccountName).
- **Statuses:** `ready`, `suspended`, `creation_failed` (`croit_rejected`: a 4xx on create that is not "already exists", cached for the TTL; invalid username; ambiguous uid; uid_taken; mapping_target_missing), `unavailable` (any croit trouble, other than a create 4xx).
- **Concurrency/cache:** per-username `asyncio.Lock`; a 400/409/422 from create re-checks `/s3/user-names` and counts "exists" as success. Results cached 5 min per username (`CACHE_TTL`), never `unavailable`. `invalidate(username=|uid=)` is called on admin mapping put/delete (AD name, old and new targets, and the targets' bare names) and suspend/unsuspend; other changes (the offboarding job and its login unsuspend do) must call it too.
- **Login:** `RgwResolver.warm` resolves in a background task after a successful login (best effort; login never waits for croit). Tests switch it off (`warm_on_login`, autouse fixture in `tests/conftest.py`).
- Frontend: `accountStatus()` in `views/credentials.js` shows the state in the Credentials card.

### Bucket keys: keys scoped to one bucket

S3 keys belong to users, not buckets, so a bucket-scoped key needs its own identity:
- **Create:** make a separate RGW user (e.g. `alice.backup-job`) and give it a zero user quota, so it can't store data in buckets of its own. Writes into the shared bucket count against the bucket owner's quota. Verify this on the real cluster.
- **Grant access:** add a bucket-policy statement that gives this user read-only or read-write access to that one bucket.
- **Ownership:** record the key's owner in SQLite.
- **Revoke:** delete the RGW user and its policy statement.
- **Offboarding:** bucket keys are suspended along with their owner.

**Code:** `bucketeer/bucket_keys.py` (module docstring has the API shapes), tests `tests/test_bucket_keys.py`, UI `components/bucket-keys-dialog.js` (a "Keys" button per bucket row).
- Own buckets only (croit-verified); uid only from the session. RGW uid `<owner>+<label>` (`tenant$owner+label`; `+` cannot occur in an AD sAMAccountName, so a key uid can never equal a human's uid, which dotted names like `john.smith` could; `s3docs` allows `+` in a principal ARN for key users only, never in Sids or shares; encode it as `%2B` for croit (`_path` and httpx params do) and as `%252B` for Admin Ops (`rgw_admin._enc`; the owner chose to keep `+` and target Tentacle, 2026-10-27, although a Reef that decodes once would store `%2B` literally), label `[a-z0-9-]` 1-20; RGW display name `bucketeer key: <owner AD> / <bucket> / <ro|rw>` (`key_display_name`; the rollback's "display name is ours" check also accepts the pre-P6-2 `Bucketeer key <label> for <owner> (<bucket>)`, `key_display_names`); refused if the uid exists in croit (case-insensitively) or in `bucket_keys` (revoked too: a uid is **never reused**). Limits (Q9, confirmed by the owner): 10 live keys per user, 5 per bucket, else 409.
- **Create is a saga** under the per-user `KeyLocks` lock plus a per-bucket asyncio lock: pending row (migration v4 adds `state` pending|active|failed and `access_key`, the public half only) -> croit user (no email) -> user quota enabled with maxSize 0 and maxObjects 0, **read back and checked, fail closed** -> exactly one generated key (croit's own auto-key is removed) -> `bucket_key_statement` (Sid `bucketeer-key-<row id>`) via `update_bucket_policy` with the OWNER's s3client -> row active. Any failure rolls back statement and RGW user, except that a croit 4xx on the user create means the user is not ours (kept), and after a timeout the user is deleted only if its display name is ours; clean rollback = row `failed` + revoked, unfinished rollback = row stays live as `failed` and shows "Needs clean-up" until a revoke retries it. A crash can leave a live `pending` row the same way.
- **Startup clean-up:** `cleanup_pending` runs as a background task from the lifespan (cancelled on shutdown; never blocks startup or `/health`; switched off in tests via `CLEANUP_ON_START`). Pending rows older than 10 min get the same `_rollback` (statement, then the user only if its display name is ours, row failed+revoked), audited `bucket_key.cleanup` (actor `system`). If the owner has no usable S3 client the row becomes `failed` ("Needs clean-up", statement and user left for a revoke). croit down: retried 3 times over ~10 min, then left until next start. Active/revoked/young rows are never touched.
- **Revoke** (idempotent): statement first (the key is dead from then on), then croit delete user (404 = fine). If croit refuses (the key user owns buckets) the row stays live with an "ask an administrator" 502; retry is safe. Bucket delete through Bucketeer revokes the bucket's keys afterwards (`revoke_for_deleted_bucket`, never fails the delete; leftovers give a `warning`).
- **Reveal:** only the row's owner (others 404), refused when the key or its owner is suspended, audited `bucket_key.reveal` first, `no-store`; same secret rules as credentials. Snippets use profile `bucketeer-<label>`. Audit `bucket_key.create|create_failed|reveal|revoke|revoke_failed`.
- Defense in depth: `RgwResolver` re-checks `uid_claimed` after get/create and answers an uncached `uid_taken`; the admin suspend cascade treats a croit 404 for a `pending`/`failed` row as done.
- moto enforces no policies, so tests assert the policy document, not enforcement. Whether RGW honours a zero user quota for a policy-granted user is the open cluster check.

Subusers (read/write/readwrite/full across *all* of a user's buckets) are offered only under Advanced. **Subuser rules (Q15, owner accepted the recommendation):** at most 5 subusers per user and 2 keys per subuser (so a key can be rotated); permissions read, write, read-write and full-control, where full-control needs a warning and an extra confirmation (it can do everything the user can, including policies, ACLs and deleting buckets); names like bucket-key labels (`[a-z0-9-]`, 1-20 characters), never reused after deletion; suspended with their user (RGW does this itself); reveal and config snippets as for the user's own keys, with profile `bucketeer-sub-<name>`. Whether RGW enforces subuser permissions for S3 (not only Swift) is a cluster check.

### Subusers (Advanced, Q15)

`bucketeer/subusers.py` (module docstring has the shapes), tests `tests/test_subusers.py` (both admin backends), UI `static/js/views/subusers.js` (a section of the Credentials card, only while `isAdvanced()`; reuses `.bkd-*` styles, own `css/subusers.css`).
- A subuser is `uid:name` with one permission (`read|write|read-write|full-control`) across ALL the user's buckets; its S3 keys appear in the backend key list with `user` = `uid:name`, so the user's own key code (`user == uid`) never sees them and `MAX_KEYS` does not count them. Permission values are croit's; the rgw client maps them to `access=read|write|readwrite|full`. The new croit calls are in `tools/croit-gate` (drift test).
- `/api/subusers` (`require_active_rgw_user`, uid only from the session, so another user's subuser is 404, no-store, per-uid `KeyLocks` around mutations): `GET` -> `{subusers: [{name, permission, keys: [{accessKey}]}], permissions, limits: {maxSubusers: 5, maxKeys: 2}}`, never a secret; `POST {name, permission, confirm?}` 201 (name `[a-z0-9-]` 1-20 like bucket-key labels; max 5 else 409; name used before, even deleted, or existing in RGW -> 409, recorded in SQLite `subuser_names`, migration v10, released only after a clean backend refusal; full-control needs `confirm`, else 409 `{requiresConfirmation}`; exactly one key from `generate_key_pair()`, read back, any failure rolls the subuser back and audits `subuser.create_failed`); `PATCH /{name} {permission, confirm?}`; `DELETE /{name}`; `POST /{name}/keys` (max 2 else 409); `POST /{name}/keys/{accessKey}/rotate` (new key first, confirmed, then the old one; allowed at the limit); `DELETE /{name}/keys/{accessKey}` (last key 409, rotate instead); `POST /{name}/reveal {accessKey}` (only a key of that subuser, audited first, no-store; the only response with a subuser secret).
- Audit `subuser.create|update|delete|create_failed` (target_type `subuser`, `uid:name`) and `subuser.key.create|rotate|rotate_failed|delete` and `subuser.reveal` (target_type `access_key`), details uid, subuser, permission, never a secret. Suspended with their user by RGW itself: no cascade. No subuser count in the admin user list. UI profiles are `bucketeer-sub-<name>`; full-control gets a warning and a confirm dialog.
- Mocks: subusers live in the shared croit mock state (`User.subusers`, subuser keys carry `subuser`), served by both the croit mock and the Admin Ops mock. The moto bridge has no subuser semantics (moto accepts any key). Cluster checks (TODO.md): S3 enforcement of subuser permissions, and how real RGW routes `PUT|DELETE /admin/user?key&subuser=`.

### Sharing

A simple, always-visible form shares a bucket with an AD user, read-only or read-write, by adding a bucket-policy statement.
- **Who can receive a share (Q8):** exactly the people who could log in. When `LDAP_REQUIRED_GROUP_DN` is set, only its members (nested membership counts); when it is empty, anyone in AD. A recipient without an S3 account yet gets one created on the spot, exactly as their first login would (same uid rules, unlimited user quota, audit), so the share works immediately and they only need to log in to get keys.
- **No group shares (Q11):** people share with individuals only. Group shares are a deferred feature on the roadmap (TODO.md "Roadmap"); don't build them.

**Code:** `bucketeer/sharing.py` (module docstring has the API shapes), tests `tests/test_sharing.py`, UI `components/share-dialog.js` ("Share" button per bucket row; `shareDialog({bucket, api, wording})`, `api.js` `bucketShares` on premises, `cloudShares` for cloud buckets) and `views/shared-with-me.js` ("Shared with you" card, following the effective location: on-premises shares on premises, cloud shares in Cloud). Cloud buckets are shared the same way, see "Cloud sharing". The `shares` table holds both kinds (`location`): `create`/`live_for`/`list_live`/`revoke_bucket` default to on-prem rows and the on-prem `_mine` checks `location`, so an on-prem path never reads, revokes or lists a cloud share.
- Recipients are exactly the people who could log in (Q8). `AdAuthenticator.lookup_user(login)` (also on `DemoDirectory`) shares `_find_entry` with login (service bind, escaped filter, exactly one, nested required group when set) and makes NO password bind; every failure is one uniform 404, directory down is 503. Lookups and share requests count against a per-owner limit (30 per 15 min, in memory). **Name search (owner, 2026-11-24):** `GET /api/people/search?q=` (`require_active_rgw_user`, no-store) is the share dialog's type-ahead (`components/person-picker.js`, reusable): `AdAuthenticator.search_people` (`ldapauth.people_filter`: every typed word, escaped, is a prefix of the username, `givenName`, `sn`, display name or email; enabled accounts only; nested required group when set; at most 10, `truncated`; under 2 characters asks nothing) returns `{people: [{username, displayName, email, isYou}], truncated}`, rate limited separately (`sharing.SEARCH_RATE_LIMIT` 150 per 15 min per user). It only suggests: the share itself still goes through the exact lookup above. Find with no exact match falls back to the search list. `DemoDirectory` and the test `FakeLdap` implement it. No group shares (Q11).
- `POST /buckets/{name}/shares {login, access}` resolves the recipient with `RgwResolver.resolve` (auto-creates the S3 account exactly like first login: mapping, case match, `uid_taken`, unlimited user quota, no email), refuses yourself, a bucket-key uid and a suspended recipient, then writes `s3docs.share_statement` with the OWNER's s3client (policy first, then the `shares` row, migration v7; at most one live row per bucket+recipient uid, sharing again changes access). The statement is the source of truth: the list shows `active`, `out_of_sync` (repair = PUT), `unknown` (a `bucketeer-share-*` statement without a row; its Sid is the id; revocable) or `unchecked`. `PUT|DELETE /shares/{id}`; revoke removes the statement, then marks the row. Bucket delete marks shares revoked. `GET /api/shared-with-me` lists live rows for the session's uid (`address` = `tenant:bucket` for another tenant). Audit `bucket.share|share_update|unshare`; each is also logged at INFO (`bucketeer.sharing`), and refusals (no audit entry) are logged with status and reason. The mailer logs its on/off state at startup and every invitation sent, skipped or failed (SMTP reply text, never the password).
- **Invitation email** (`bucketeer/mailer.py`, `app.state.mailer`, tests `tests/test_mailer.py`): a NEW share (not an access change) emails the recipient's AD `mail` with the owner's name, the bucket's short name, the access and the `APP_URL` login link; never a key or URL that grants access. Email is on only when `SMTP_FROM` is set (`SMTP_HOST` alone changes nothing), and then `APP_URL` is REQUIRED. `SMTP_HOST` empty = direct delivery to the recipient domain's MX (dnspython, lowest preference first, at most 3 hosts, port 25, unverified STARTTLS when offered); set = that relay with `SMTP_PORT`/`SMTP_SECURITY`/`SMTP_USERNAME`/`SMTP_PASSWORD`. The mail is sent in a background task after the answer (a slow server never holds up the share); the share answer carries `emailed` (`"queued"`, or null = off). A failed email never fails the share and is logged by exception type only. `SMTP_USERNAME` with `SMTP_SECURITY=none` is refused at startup (the login would travel in clear text). Names are stripped of control characters before going into the subject.

### Bucket policy and lifecycle are shared documents

Several features write the same per-bucket policy and lifecycle configuration: bucket keys, sharing, simple lifecycle rules, and the Advanced raw editors.
- Read-modify-write them, and only touch statements or rules whose `Sid`/`ID` starts with `bucketeer-` (e.g. `bucketeer-key-<id>`, `bucketeer-share-u-<uid>` or `bucketeer-share-t-<tenant>-<uid>`).
- Leave every other statement intact.
- The raw editors show everything but must warn before editing `bucketeer-*` entries.
- Policy principals are `arn:aws:iam::<tenant>:user/<uid>`, with an empty tenant when there is none.
- **Always use `bucketeer/s3docs.py`** (pure document functions plus `update_bucket_policy` / `update_bucket_lifecycle` / `update_bucket_tagging`). Never call `put_bucket_policy`, `put_bucket_lifecycle_configuration` or `put_bucket_tagging` directly. The helpers refuse to write non-`bucketeer-*` entries, raise on duplicate Sids/IDs, and delete the document when the last entry goes (S3 rejects empty ones). Builders: `share_statement`, `bucket_key_statement`, and the three simple lifecycle rules. Their action sets are documented in the module docstring.
- The helpers are synchronous: call them with `asyncio.to_thread`. There is no conditional write, so they take `bucket_lock(bucket)` (per-bucket, re-entrant); hold it yourself around any multi-step change to one bucket. Writers outside this process can still cause a lost update.

### User S3 calls and the bucket API

- **`bucketeer/s3client.py` (`app.state.s3`, `S3Clients`) is the only way to make S3 calls for a user.** `await s3.call(uid, fn, *args)` builds a per-request boto3 client from the user's OWN first croit key (never from the browser; no admin S3 identity), endpoint as in credentials, addressing style, region, `when_required` checksums, modest retries/timeouts, and runs `fn(client, ...)` via `asyncio.to_thread`. ### Offboarding job

`bucketeer/offboarding.py` (module docstring has the API shapes), tests `tests/test_offboarding.py`, UI `views/admin-offboarding.js` ("Offboarding" tab; `.off-*` at the end of `css/settings.css`). Implements the Q10 safeguards above; `app.state.offboarding` (`OffboardingService`).
- **Scope:** migration v8 `known_accounts` (`ad_username`, `rgw_uid`, `source` created|linked|mapping, `first_seen`, `last_login`, `offboarding_suspended_at`). `RgwResolver.record_link` writes it on every uncached resolution of a person (login, warm, share/ACL recipient created on the spot; never a bucket-key uid, `rgw_user.is_key_uid`); each run also records admin mapping targets that exist in croit. Re-linking an AD name to another uid drops the flag. People = known rows whose RGW user exists in croit; everything else is never touched.
- **AD check:** `AdAuthenticator.account_statuses(names)` (one service bind, exact escaped `LDAP_USERNAME_ATTRIBUTE` search, not the login filter) -> `ok|disabled` (userAccountControl bit 2) `|not_in_group` (nested required group, when set) `|not_found`; any LDAP trouble (down, ambiguous, no userAccountControl) raises `LdapUnavailable` and aborts the run. `DemoDirectory.account_statuses` has `disabled` / `left_group` sets (`mock/demo.py --disabled bob`); the fake LDAP in `tests/test_auth.py` understands `userAccountControl` and `fail_search`.
- **Run:** candidates = known people not already suspended in croit (an admin's suspension is never touched) whose every AD name is not `ok`. Abort rule (Q14, admin settings on the Offboarding tab, validated 422 `{detail, errors:[{field,message}]}`, audited in `admin.settings.offboarding` with before/after; stored settings without the keys use the defaults): with C candidates and K known people (suspended ones included) abort when `C*100 > maxPercent*K` (default 10, 1..100) AND `C >= minPeopleForPercent` (default 4, 1..1000), OR `C > maxPeople` (default 20, 1..100000); the comparisons are exact (strictly more than the share, at least the minimum, strictly more than the people limit), so 1 of 4 passes and 4 of 20 aborts with the defaults; an LDAP error always aborts. Aborted -> outcome `aborted`, nobody suspended, reason (quoting the limits) stored and audited. The limits in force are stored in the run's `counts.thresholds` and returned as `thresholds` per run (shown in the run report); `GET` has no top-level `thresholds` any more. Report mode only records `would_suspend`. Enforce suspends each candidate in croit, then the owner's live unsuspended bucket keys through `admin.apply_key_suspension` (shared with the admin routes) with `suspended_by='offboarding'`, sets the flag, invalidates the resolver cache, audits `offboarding.suspend` per user; a person who logged in during the run is skipped. One run at a time (`running` flag, `AlreadyRunning`); runs are stored in `offboarding_runs` (last 30, per-person results capped at 200, stale `running` rows failed at start). Outcome `ok|aborted|failed`.
- **Exact uids, one lock:** croit uids are matched exactly (`alice` is not `Alice`; `known_accounts.for_uid`/`clear_offboarding_for_uid` are exact). A known uid that exists in croit only in another case is skipped with a note (`uid_case_mismatch`), never guessed; a mapping target must exist exactly. Rows with source `mapping` whose mapping was deleted or re-pointed leave the scope (`admin_settings` put/delete drop them; the run ignores stale ones). The flag is set BEFORE the croit PATCH and released only on a definite 4xx; a timeout/5xx keeps it (result action `unknown`, counted as failed) so a login restores the account. `OffboardingService.lock` serializes the job's per-person suspend, `on_login` (which reads the flag only inside it) and admin `_set_suspended` (via `get_suspend_lock`). A changed run time counts from the change (`note_settings_changed`), never firing a run at once.
- **Finishing keys:** an account the job flagged and croit shows suspended, but whose owner still has live unsuspended bucket keys (an earlier `unknown` suspend), is listed as `keys_pending` (counts `keysPending`); an enforce run suspends those keys (`suspended_by='offboarding'`, same helper and lock), result action `keys_completed`, audit `offboarding.suspend` with `keys_only: true`.
- **Coming back:** `RgwResolver.on_login` (post-login warm-up, never blocks login) -> `OffboardingService.on_login`: only when the person's flag is set, unsuspend the RGW user and only keys with `suspended_by='offboarding'`, clear the flag, invalidate, audit `offboarding.unsuspend` (actor `system`; a failure audits `offboarding.unsuspend_failed` and keeps the flag for the next login). `admin._set_suspended` clears the flag first: an admin suspend takes over (the job's keys are relabelled `owner`, never undone by a login), an admin unsuspend settles it and also wakes the job's keys.
- **Schedule:** `schedule_loop` is a lifespan task (cancelled on shutdown, never blocks startup or `/health`; `offboarding.SCHEDULE_ON_START`, off in tests by an autouse fixture) that sleeps in <=60 s ticks, re-reading the settings, and runs at the first `HH:MM` strictly after the last one (`next_run`); `now` and `sleep` are injectable. Settings key `offboarding` `{mode: report|enforce, time: "HH:MM"}`, default report and 03:00 server local time.
- **API** (`/api/admin/offboarding`, admin, CSRF): `GET` -> `{settings, running, nextRun, knownPeople, thresholds, runs[{id, startedAt, finishedAt, mode, trigger schedule|manual, actor, outcome, reason, counts, results[{uid, adUsernames, reason, action, keys, note?}]}]}`; `POST /run` runs inline and answers with the finished run (409 while one runs; the job is a task a dropped connection does not cancel); `PUT /settings {mode?, time?}` (422 for anything else) audits `admin.settings.offboarding` (target_type `setting`) when changed. The UI asks for a confirm before switching to enforce.
- **Audit:** `offboarding.run|aborted|run_failed` (target_type `offboarding_run`, target run id; actor `system` for scheduled runs, else the admin), `offboarding.suspend|unsuspend|unsuspend_failed` (target_type `rgw_user`).

### Backup (admin, P6-7)

Owner decisions: backups hold the database and `.env` only, are not encrypted by Bucketeer (the object-locked bucket protects them), and `.env` names the on-prem bucket while the admin page sets time and retention. `bucketeer/backup.py` (module docstring has the shapes), tests `tests/test_backup.py` (both backends, moto), UI `views/admin-backup.js` ("Backup" tab, `.bu-*` at the end of `css/admin.css`). `BACKUP_BUCKET` (Default empty = off; validated with `check_dns_name`; while cloud is configured it must be `<CLOUD_BUCKET_PREFIX>backup-<12 lowercase hex>` (`config._check_backup_name_for_cloud`), because the AWS copy has the SAME name; while empty the lifespan logs and the tab shows a suggestion of that form, the app never writes `.env`). Owner: RGW user `bucketeer-backup` (`croit.BACKUP_UID`) created through the admin client on the first run, key read from the admin client each time (one generated with `generate_key_pair` if it has none), never stored. **It is treated like the Admin Ops service user:** `croit.is_backup_uid` (bare uid, any case/tenant) filters it from `list_users`/`list_user_names`/`list_buckets` on BOTH clients, and `rgw_user.is_service_uid` answers True for it (login, mapping, share/ACL, admin suspend/quota refused). The bucket is created idempotently with its own boto3 client (`OnPremDestination`, `s3client.default_factory`, TLS settings; tests spy on `app.state.backup.factory`), object lock at create, default retention COMPLIANCE `retentionDays` (never shortened), lifecycle `bucketeer-backup-expire|noncurrent|markers` via `s3docs.update_bucket_lifecycle`. Each run uploads `backup/bucketeer-YYYY-MM-DDTHHMMZ.tar.gz` (`Database.snapshot` via the sqlite backup API, the `.env` that `load_settings` read (`backup.ENV_FILE`, tests patch it; missing = note), `meta.json` with hashes and row counts) with `ContentMD5`; success removes the pre-upgrade copies (`Database.remove_upgrade_copies`). One run at a time (409), shielded task. Runs (last 30, newest first) live in the settings key `backup_runs`; settings key `backup` `{time, retentionDays}` (defaults 03:00, 30; retention only lengthens, applied to the bucket at once, best effort). Routes `/api/admin/backup` (GET state, never creates anything), `PUT /settings`, `POST /run`; audit `admin.settings.backup`, `backup.run`, `backup.failed` (target_type `backup`, target the bucket; actor `system` for the schedule). `schedule_loop` is a lifespan task (`backup.SCHEDULE_ON_START`, off in tests by an autouse fixture). Restore: `python3 app.py --restore-backup <key|latest> [--force]` (`restore_main`): refuses while `/health` answers on `PORT`, verifies every SHA-256, integrity-checks, keeps the old database as `.replaced-<time>` (WAL folded in), installs the new one, opens it with `Database()` (migrations), writes `.env.restored-<time>` 0600 next to the live `.env` (never over it), calls `rebuild_from_ceph(fill_gaps=True, ...)` if a module in `CATCH_UP_MODULES` provides one (else says catch-up isn't available), prints `rebuild.summary(report)`, audits `system.restore` into the restored database with only `catch_up_digest(report)` (mode, counts, reasons, at most 50 problem items). Destinations are a small class interface (`ensure/inspect/upload/download/latest`) picked per run by `BackupService.destinations()`.

### Audit log viewer

`bucketeer/audit_viewer.py` (router `/api/admin/audit`, `require_admin`, tests `tests/test_audit_viewer.py`). `GET /api/admin/audit?actor=&action=&target_type=&target=&target_contains=&since=&until=&limit=&before_id=` -> `{entries:[{id, ts, actor, action, targetType, target, details}], nextCursor}`, newest first by id; `action` ending in `.` is a prefix match (`bucket.`), else exact; `target` exact, `target_contains` case-insensitive substring; `since` inclusive, `until` exclusive, ISO 8601 (naive = UTC); `limit` default 50, silently capped at 200 (<1 -> 422); `nextCursor` is the last id of a full page, pass it as `before_id` (stable under concurrent inserts). ### Admin settings

`bucketeer/admin_settings.py` (routes `/api/admin/settings`, admin only, CSRF via the parent router) and `bucketeer/policy_settings.py` (pure validators and helpers later features call). `GET /settings` returns everything. Stored in `settings` (keys `naming` {prefix, pattern}, `placement` {default, allowed}, `budget_number` {pattern, example}, `bucket_quota` {defaultQuotaTiB, maxWeeklyQuotaIncreaseTiB}, legacy `default_quota` (read only by the one-time unlimited step), `notification_endpoints` list) and the `uid_mappings` table; load with `load_*`. Each change audits `admin.settings.*` with before/after.
- **Naming:** DNS-compatible rules always (`check_dns_name`), and **no dots, only hyphens** (owner, 2026-10-27: buckets are used virtual-host style behind a wildcard certificate, which covers one label; the `{username}` slug turns dots into hyphens too; existing dotted buckets stay manageable, only new names are checked); optional prefix template (`{username}` only, slugged lowercase, `_` becomes `-`) and optional extra regex (fullmatch, max 200 chars). `validate_bucket_name(name, username, rules) -> [errors]`, `suggest_prefix`. Regex safety layers: a static pre-check (`check_pattern_static`: counted repeats above 63, nested product above 256, since `regex` expands them at compile time), then `approve_pattern` compiles and probes in a subprocess (256 MB cap; the child times its own compile and probes against a 1 s budget, so interpreter start-up never counts; the outer kill is 10 s), then in-process matching on the `regex` module with a 50 ms `timeout=` for approved patterns only (bounded cache). These can block briefly: call `normalize_naming`/`validate_bucket_name` via `asyncio.to_thread`. `POST /settings/naming/test` tries draft rules without saving. Use `\Z`, not `$`, when validating whole strings (`$` accepts a trailing newline).
- **Placement:** validated on save against croit `GET /s3/placements` (`CroitClient.list_placements`). Default null = croit's zone default; allowed [] = users get no choice. `placement_options()` gives the create-form view; the choice is shown only when `userChoice` (more than one).
- **Bucket quotas (P6-4):** `PUT /settings/bucket-quota {defaultQuotaTiB?, maxWeeklyQuotaIncreaseTiB?}` (partial, 1..100000, defaults 1 and 100; `bucket_quota.normalize_settings`), `GET /settings` `bucketQuota` = `{defaultQuotaTiB, maxWeeklyQuotaIncreaseTiB, isSet, defaults, maxBucketTiB, maxWeeklyTiB}`, audit `admin.settings.bucket_quota`. The old `PUT|DELETE /settings/default-quota` stay as compat aliases for the default bucket quota (`{quotaTiB}` or the old `{enabled: true, maxSize}` rounded up; DELETE = 1 TiB). The old user `default_quota` / `DEFAULT_QUOTA` / `effective_default_quota` are legacy: only `bucket_quota.unlimit_user_quotas` reads them.
- **Budget numbers (Q2):** `PUT /settings/budget-number {pattern, example}` (both optional, empty pattern = base charset rules only) via `budget.normalize_budget_rules`: pattern through the naming guards (length, static check, `approve_pattern`), example must pass base rules and the pattern; audit `admin.settings.budget_number` (target_type `setting`). `POST /settings/budget-number/test {rules, value}` is a dry run (exempt in the audit test). `GET /settings` has `budgetNumber`; `budgetExample` is exposed by `GET /api/profile` and `GET /api/buckets/options`. Changing the pattern never alters stored numbers; `GET /api/admin/buckets` adds `budgetMatches` (true/false, null = no number or no pattern) and the table shows a "Format mismatch" badge.
- **Chargeback export (Q2):** `GET /api/admin/export/chargeback.csv` (admin; `text/csv; charset=utf-8`, attachment `bucketeer-chargeback-YYYY-MM-DD.csv`, `no-store`). One row per bucket (key users own none): `bucket` (tenant-qualified), `tenant`, `owner_uid`, `owner_name` (RGW display name), `budget_number`, `budget_status` (`ok`|`missing`|`mismatch`|`unknown` = pattern check timed out or was cut off; no pattern set means any number is `ok`), `objects`, `bytes`, `size_gib` (3 decimals), `quota_bytes` (empty unless the bucket quota is enabled with a size), `created_at` (empty for buckets not made through the portal), then (P6-14, appended) `location` (`onprem`|`cloud`) and `product` (catalog name: Tier-3-S3 on prem, the cloud bucket's product). Cloud rows (Q19): bytes/size_gib from CloudWatch (empty when unknown), objects empty, quota_bytes = quotaTiB*2^40. Every cell goes through `csv_safe` (leading `=+-@` tab CR gets a `'`; budget numbers and display names are user text). **UTF-8 with BOM** (Excel then reads it right); CRLF lines. Audited `admin.export.chargeback`, target_type `report` (a GET, so not in the audit ROUTES table). Admin Buckets tab has an "Export CSV" link (all buckets, ignores filters). Tests: `tests/test_chargeback.py`.
- **UID mappings:** `PUT/DELETE /settings/uid-mappings/{ad}`; uid syntax `uid` or `tenant$uid`; unique both ways (case-insensitive, 409); a missing RGW user is a warning only. Applied by `rgw_user` at resolution.
- **Notification endpoints:** `PUT/DELETE /settings/notification-endpoints/{name}`; types http|https|amqp|kafka with matching schemes, `topic` = the AMQP exchange, REQUIRED for amqp (422 on save) and REFUSED for kafka (the Kafka topic is the per-user RGW topic `bucketeer-<endpoint>-<user>`; the broker must auto-create topics; the UI hides the field and warns on stored entries that still have one), `verifyTls`. ### Always visible vs. Advanced

- **Always visible:**
  - the "Set up this computer" panel (one-time setup command, owner 2026-10-27) and the account status; keys, secret and config snippets are Advanced only
  - (Advanced) key create, rotate and delete. Rotation adds the new key before removing the old, never with a whole-set PUT that drops keys. At most 5 keys per user, and a user's last key can't be deleted, only rotated (confirmed by the owner).
  - bucket list, create and delete. Deleting any bucket requires typing its name; with content the dialog shows the objects and space that go (owner, 2026-11-25).
  - versioning: **on by default** for new buckets (Q7), and a new versioned bucket also gets the Bucketeer-managed lifecycle rule "expire noncurrent versions after 30 days" (`bucketeer-expire-noncurrent`). Users can untick versioning or change the rule.
  - usage and the bucket quota (whole TiB) with its monthly cost whenever a quota is picked (Phase 6 decision 1)
  - sharing and bucket keys
  - presigned share links (at most 7 days)
  - simple lifecycle rules: expire after N days, expire noncurrent versions, abort incomplete multipart uploads
- **Advanced:** one global toggle, remembered per user (`user_profiles.advanced_mode`, returned as `advancedMode` by `/api/me` and `/api/profile`, saved with `PUT /api/profile {advancedMode}`; frontend store `static/js/advanced.js`: optimistic with rollback + toast, no localStorage hint; gated UI reads `isAdvanced()` / `subscribe()` so it reacts without reload):
  - the raw bucket-policy editor and ACLs
  - CORS and tagging
  - object lock: offered only in the create-bucket dialog with a can't-be-undone warning, plus retention and legal hold
  - the full lifecycle editor
  - notifications: endpoints only from the admin-defined list
  - multipart cleanup
  - subusers
  - placement and storage class choice, shown only when more than one exists
  - the Cloud / On Premises switch (only when cloud is available). Advanced only unlocks the switch: the saved choice keeps applying when Advanced is turned off; a user with no saved choice gets the global default.
- **Budget numbers** (index/worktag, Q2):
  - Users must enter a budget number for every bucket they create. A default saved in their profile prefills the form. **Only admins** can create a bucket without one.
  - **Format:** checked against an admin-editable pattern on the Settings tab, with an example shown as a hint. There is no lookup against a finance system.
  - **Storage:** kept in SQLite (`buckets.budget_number`) and mirrored as the Bucketeer-managed bucket tag `bucketeer-budget=<value>`. The tagging editor protects `bucketeer-*` tags.
  - **Editing:** the bucket owner can change it later; the audit log records the old and new values.
  - **Existing buckets without one** are flagged in the bucket list and on the admin page, but not blocked.
  - **Reporting:** the admin page offers a CSV chargeback export (bucket, owner, budget number, usage) and the monthly chargeback .xlsx (Billing tab, emailed to the billing contacts); buckets without a number stay in the sheet with an empty Index and a Problems entry.
- **Budget gate (owner, 2026-11-21):** `profile.require_default_budget` (a route dependency) refuses non-admins with 409 `{detail, budgetMissing: true}` until a default budget number is saved, on bucket create, own key create, setup link, subuser create, subuser key create and bucket key create. Reveal, rotate, delete and reads stay open. `api.js` fires `bucketeer:budget-missing` and `app.js` goes to `#/profile`. `REQUIRE_DEFAULT_BUDGET` is off in tests (conftest) except `tests/test_budget_gate.py`.
- **Profile** (`bucketeer/profile.py`, `/api/profile`, `require_user`, CSRF, keyed by the session's AD username, never by the request): `GET` -> `{username, displayName, email, defaultBudgetNumber|null}`; `PUT {defaultBudgetNumber?: string|null, advancedMode?: bool}` is a partial update (only the fields present change; null/empty budget clears; unknown fields or null `advancedMode` 422), audits `profile.update` (`field`, `old`/`new`, per field, only when changed). `GET` also has `advancedMode`. `budget.validate_budget_number(value, settings_store)` is pure: trim, max 64, printable, only S3 tag-value characters (the value is mirrored into a tag): ASCII letters/digits/space/`+-=._:/@` (no `#`, no non-ASCII), then, if the `budget_number` setting `{pattern, example?}` exists (the later admin-editable format), the value must fullmatch it through `policy_settings.pattern_matches` (approved patterns only; call via `asyncio.to_thread`). Reuse it for the per-bucket budget number. Frontend: `views/profile.js`, route `#/profile`, header-menu link. **Default budget number is expected from every user (owner, 2026-11-20):** `GET /api/me` has `budgetMissing` (no default saved); while it is true, `app.js` opens `#/profile` first after each login or page load (not on later navigation), and the profile shows a notice with the example `DN099999` (the admin's `budgetExample` wins in the field hint) plus a "Go to my workspace" link; a "Back to my workspace" link is always at the top. - **Storage classes (Q6):** on premises users choose only a placement for a new bucket, never a storage class. Cloud buckets choose Intelligent-Tiering or Deep Archive per bucket (Phase 6 decision 7, a day-0 lifecycle transition).

### Admin page and storage

- Runtime policy is edited on the admin page, not in `.env`: bucket naming rules, placement defaults, bucket quota settings, uid mappings, and the notification endpoint allowlist. `.env` keeps only infrastructure and secrets.
- State lives in **SQLite** under `DATA_DIR`. That covers settings, uid mappings, bucket-key ownership and the **audit log** of who created or deleted buckets, keys and shares.
- `DATA_DIR` defaults to `data/` in the repo (git-ignored). appmotel updates use `git reset --hard`, which keeps ignored files, and its backups and restores tar the repo, so the database is included.
- Assume a single uvicorn process: SQLite plus in-process background jobs such as the offboarding sync.
- **Code:** `bucketeer/db.py`. The file is `DATA_DIR/bucketeer.sqlite3` (WAL; file and `-wal`/`-shm` 0600; a data dir Bucketeer creates is 0700, an existing one keeps its mode and logs a warning if group/other can access it). `create_app` opens it in the lifespan (`app.state.db`, `get_db` dependency) and closes it on shutdown; tests pass `create_app(settings, db=Database(":memory:"))`. `/health` never touches it.
  - One connection behind an RLock; repositories (`db.settings`, `uid_mappings`, `profiles`, `buckets`, `bucket_keys`, `audit`) are sync and return plain dicts. Async handlers call `await db.run(db.buckets.get, name)`. Multi-statement writes use `with db.tx():`.
  - **Migrations:** `MIGRATIONS` in `db.py`, tracked by `PRAGMA user_version`, each applied in one transaction at startup (an old installation goes through every missing one). An entry is a SQL script or a Python step `fn(conn)` (runs inside the transaction: `execute` only, never `executescript`/COMMIT; make it idempotent). Append a new migration, never edit an applied one. Before upgrading an existing file database (version > 0) it writes a consistent copy `<file>.pre-v<old>-<UTC time>` (sqlite backup API, 0600, newest `KEEP_UPGRADE_COPIES`=3 kept). A failing migration (or copy) raises `MigrationFailed` naming the migration number, the cause and the copy, and the app refuses to start. The app refuses to start on a database newer than the code. `tests/test_db_upgrade.py` builds a database at every past version from `MIGRATIONS[:n]` with `SAMPLES` rows and upgrades it: a new migration is covered automatically, add sample rows for its new tables (`test_samples_cover_every_table` insists) and `BACKFILLS` for data it fills in.
  - **Audit log** is append-only: use `db.audit.add(...)` (no update/delete helpers exist). Never put secrets in `details`; keys named like secret/password/token are redacted as a safety net, not a license.
  - **Audit coverage (enforced):** `tests/test_audit_coverage.py` is the source of truth. Its `ROUTES` table maps every POST/PUT/PATCH/DELETE route (taken from the OpenAPI document) to its audit action(s); a new mutating route missing from the table fails the test, and each entry is exercised once against the mock croit + moto. `EVENTS` lists the non-route actions (`bucket_key.cleanup` by actor `system`, `rgw.user.*`, the `*_failed` ones). Scheme: `area.verb[.detail]` (lowercase, `_` inside a word); `logout` is the one old exception. Actor is the AD username (`system` for background jobs; the attempted name on `login.failure`). `target_type`/`target`: `bucket` + croit name (tenant-qualified), `rgw_user` + uid (also `admin.user.*`, `rgw.user.*`), `bucket_key` + row id, `access_key` + access key (`credentials.*`), `profile` + username, `setting` + settings key (`admin.settings.naming|placement|default_quota`), `uid_mapping` + AD name, `notification_endpoint` + name, `user` + AD name (login/logout). Mutations whose outcome is unknown after a failure (croit timeout, failed task, 5xx) audit `bucket.create_failed|delete_failed|versioning_failed` (a plain 4xx refusal changed nothing and is not audited). A scan over all rows from that run fails on secret keys, `Signature=`, Bearer tokens or passwords. Renames made then: `target_type` `user`->`rgw_user` (admin.user.*), `user_profile`->`profile`, `settings`->`setting`; action names unchanged.
  - `settings` takes caller-supplied defaults (`db.settings.get(key, default)`); the schema holds no policy values. `buckets.budget_number` is nullable and unvalidated until Q2 is answered.

### Later features

These need cluster work first:
- **Server-side encryption** needs a key server (Vault, Barbican or KMIP).
- **Static website hosting** needs RGW website mode and wildcard DNS.
- **STS temporary credentials** need an STS key and roles on RGW. They would also give short-lived bucket-scoped keys.
